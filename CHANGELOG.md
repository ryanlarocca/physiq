- **August 27, 2026** — **AI logging hang fixed: auth check now verifies the Supabase JWT locally (JWKS/ES256) instead of a network round-trip.** Ryan reported photo+caption logging freezing on "🤖 Analyzing photo…" and then `❌ FetchEvent.respondWith received an error: TypeError: Load failed`; he suspected the Mac mini reboot (unrelated — the mini isn't in this path). **Diagnosis (measured):** `physiq-api` was up and Anthropic direct was 1.6s, but end-to-end `parse-meal` took **47s** and `parse-meal-photo` **110s**; a bogus-token request took 98s to return 401 while `/api/debug` was 0.2s → the hang was entirely inside `verifyUser`'s `fetch(SUPABASE/auth/v1/user)` from Vercel. Cause: **Supabase incident that morning** ("Increased response times for requests" + "401 errors due to JWT rejections", opened ~10:20 PT). The client aborts at 90s and iOS's service-worker-proxied fetch dies earlier with that "Load failed" text. **Fix (`physiq-api/api/_auth.js`):** verify the user token **locally** — user JWTs are ES256 signed with the key published at `/auth/v1/.well-known/jwks.json`; the key is imported via Node webcrypto, cached for the warm lambda, refreshed on unknown `kid`; checks signature + `iss` + `aud=authenticated` + `exp`. Network verification remains only as a fallback (non-ES256/unknown kid) and is **bounded to 8s** (also the JWKS fetch), throwing `AuthUnavailableError` → all four gated routes (`parse-meal`, `parse-meal-photo`, `notify-login`, `submit-bug`) return **503 "Sign-in check timed out (Supabase slow). Please try again."** instead of hanging. No secrets needed (public JWKS). **Verified:** unit — valid token 84ms (0ms cached), tampered payload → null, garbage → null, HS256 anon key → fallback → null; prod e2e after deploy — text **2.2s**, photo **5.7s** (same Cheerios label), bogus token 401 in 0.3s. **Deployed:** `physiq-api` via `vercel --prod` (`physiq-5gdnvpwb7`). No app (`index.html`/SW) change. **Note:** `physiq-api` source lives at `~/Projects/PROJECTS/_archive/physiq-api` and is **not git-tracked** (gitignored under `_archive/`) — Vercel deployment is the source of truth.

- **July 16, 2026** — **Slow-load fix: instant open from a local data cache + timeouts everywhere + weight-entry dedup/upsert.** Ryan reported ~2-minute blank screens opening the app since the multi-user launch. **Diagnosis (measured, not guessed):** the DB is fine — tables are tiny (277 weights / 723 macros / 5 users), pg_stat_statements shows zero slow app queries, and a headless login against prod loaded in 0.7s warm / 7.5s cold. The real cause: the June 29 launch moved data from localStorage (instant, offline) to a strictly **sequential, unbounded-timeout network chain** (getSession → probe → weights → macros) that blocks all rendering — one stalled request on PWA resume (dead connection, OS-level timeout ≈60s+) = minutes of blank screen. **Fixes (`index.html`):** (1) **local data cache** (`physiq_data_cache_v1`) — last known-good weights+macros painted instantly on startup, network only reconciles in background; cleared on sign-out. (2) startup + focus refreshes now **parallel + wrapped in `sbOp`** (8s timeout, retry) — the helper existed but was never applied to the loads. (3) **`getSessionFast()` watchdog** — getSession raced against 4s, falls back to the stored session (auth reconciles via onAuthStateChange; TOKEN_REFRESHED re-runs loadAppData if startup ran on a stale JWT). (4) **write-generation guard** — a background refresh whose response predates a mid-flight write is discarded instead of silently rolling the write off the screen. (5) **true DB upsert for weights** — new unique index `weight_entries_user_date_key` + `on_conflict=user_id,date` / `resolution=merge-duplicates`; the old cache-decides-insert-or-update path had already created duplicate date rows (2026-06-23, 2026-07-10 — deduped, CSV backup taken first). (6) **`user_goals` table created** (RLS + authenticated grant) — the app had been 404ing on it every load since launch, so macro goals never actually synced. (7) **SW `v10`**: HTML network-first now has a **3.5s cutoff → cached copy** (network keeps updating the cache in background), so a stalled index.html fetch can't blank the PWA either. Migration: `migration-2026-07-16-perf-integrity.sql`. **Verified:** existing suites all green (UI 12/12, isolation 10/10, gym 11/11) + new `scripts/test-perf-fix.mjs` **7/7** — incl. "all Supabase calls stalled → data visible in 0.08s" (the old 2-minute case) and "same-date re-log after cache wipe → still one row". **Deployed:** GitHub Pages from `main`.

- **June 15, 2026** — **Weight chart Y-axis now zooms to actual weights — the goal line was stretching the chart.** Ryan flagged that the weight chart looked too "flat" — current weights cluster ~191–196 but the chart bottom was anchored down at 171 because the **goal weight of 175** was being treated as a data point, pulling `yMin` down and burning ~20 lbs of vertical space on a region with no data. **Root cause:** Chart.js's default auto-scaling considers every dataset (weights, 7-day avg, 30-day avg, and the horizontal goal line) when computing `min`/`max`, then adds its own padding — so a goal point well outside the actual weight cluster anchors the axis to itself. **Fix:** compute `yMin` / `yMax` manually from **visible weights + the 7-day moving average only** (goal explicitly excluded from the bounds calculation), apply a 15% buffer, `Math.floor` / `Math.ceil` to clean integers, and wire those into the y-axis scale config. The goal line still renders on the chart; it just no longer drags the axis around. **Files:** [`index.html`](./index.html) — bounds computation at ~lines 2840–2848, y-axis scale config a few lines below. **Commits:** `dd9cdf7` "Weight chart: dynamic Y-axis scaling to actual data range" + follow-up `0d34c6b` "fix(chart): exclude goal from Y-axis bounds so chart zooms to actual weights" (first pass still included goal in bounds; second pass fixed it). **Verified:** chart on live site now zooms tight to the 191–196 cluster with a small buffer; goal line at 175 still visible; works across 7D / 14D / 30D / All ranges. **Deployed:** GitHub Pages auto-deploy from `main`.
